**Платформа:** Linux
**Команда:** Менеджер · Аналитик · Разработчик · Тестировщик (QA)
**Заказчик:** Емельянов Д.М.

## 1. Объём работ

| ID | Требование | Уровень |
|----|-----------|---------|
| F1 | По номеру группы: список студентов с наилучшей посещаемостью за заданный период | База (обязательно) |
| F2 | По номеру группы: имя студента с максимальным общим числом правильных ответов + это число | База (обязательно) |
| F3 | По фамилии: вывод досье студента; удаление досье(или студента - уточнить) после подтверждения пользователя | «Отлично» |
| F4 | Список группы, упорядоченный по успеваемости, с выводом значения | «Отлично» |
| D1 | Краткая документация решения (руководство пользователя, примеры запуска) | Отчётность |
| D2 | Отчёт о тестировании | Отчётность |
| D3 | Документирование хода разработки: проект на GitHub с историей тестирования и исправлений | Отчётность |
| D4 | Задача «Готов к защите» от каждого участника | Отчётность |

Исходные данные: Файловая Система Преподавателя (ФС) из ЛР 3.

## 2. Стратегия

**Облегчённый итеративный подход (Scrum-lite) + Kanban-доска в GitHub Projects.**

- **Две итерации примерно по неделе.** Каждая заканчивается проверенным результатом.
- **Сначала MVP.** Первая итерация доводит до рабочего и протестированного состояния только базовые требования (F1, F2), и сдача гарантирована. Требования на «отлично» (F3, F4) делаются только во второй итерации.

## 3. Этапы и вехи


| Этап | Результат (веха) |
|------|------------------|
| **Итерация 0. Запуск** | **M0:** требования уточнены, репозиторий и доска готовы |
| **Итерация 1. База (F1, F2)** | **M1:** F1 и F2 работают и проверены, сдача обеспечена |
| **Итерация 2. «Отлично» (F3, F4)** | **M2:** заморозка функциональности |
| Стабилизация | Регрессия пройдена, документация и отчёт о тестировании готовы |
| Подготовка к защите | Все закрыли задачу «Готов к защите», проведена репетиция |
| **Защита** | Менеджер присутствует обязательно |

### Итерация 0. Запуск
- **Менеджер:** создать репозиторий, доску, метки и чат команды; провести стартовый созвон; завести первые задачи.
- **Аналитик:** составить список вопросов к заказчику.
- **Менеджер + Аналитик:** уточнить требования у заказчика.
- **Разработчик:** выбрать средства разработки, подготовить окружение.
- **Аналитик и QA:** изучить общую ФС из ЛР 3. QA параллельно продумывает, какие данные понадобятся для тестов.

### Итерация 1. База
- **Аналитик:** спецификация v1: архитектура, интерфейс, формат вывода, пользовательские сценарии для F1 и F2.
- **Разработчик:** каркас решения, затем F1 и F2; базовое (dev) тестирование.
- **QA:** подготовить тест-кейсы по спецификации и синтетические данные; протестировать F1 и F2.
- **Менеджер:** следить за доской, снимать блокеры, расставлять приоритеты багов.

### Итерация 2. «Отлично»
- **Аналитик:** в начале итерации дополнить спецификацию для F3 и F4; затем руководство пользователя и примеры запуска.
- **Разработчик:** реализовать F3 и F4, исправлять баги.
- **QA:** тестировать F3 и F4 (особенно удаление), проводить регрессию F1 и F2.

### Стабилизация и защита
- **QA:** финальная регрессия, отчёт о тестировании, подтверждение готовности.
- **Аналитик:** финальная версия документации.
- **Все:** закрыть свою задачу «Готов к защите».
- **Менеджер:** провести репетицию демонстрации, присутствовать на защите; после защиты провести разбор результатов.

## 4. Правила работы

- **Любая работа оформляется задачей (Issue)** на GitHub с ответственным и сроком.
- **Колонки доски:** Backlog → To Do → In Progress → Testing → Done.
- **Метки:** `feature`, `bug`, `docs`, `test`.
- **Баг тоже оформляется задачей** с меткой `bug`. Исправление ссылается на задачу (`Fixes #N`), так история тестирования и исправлений видна на GitHub.
- **Ветки и Pull Request** для изменений .
- **Ежедневный короткий отчёт в чате** в формате «сделал / сделаю / мешает».
- **Созвоны:** в начале и в конце каждой итерации, плюс «горячие звонки» по необходимости.
- **Критерий готовности (Definition of Done)** . Функция готова, когда:
  1. реализована;
  2. проверена QA по тест-кейсам;
  3. описана в документации.

### Структура репозитория
```
README.md                    — о проекте, команда, как запустить
docs/plan.md                 — план проекта (менеджер)
docs/roles/*.md              — зоны ответственности ролей
docs/spec.md                 — спецификация (аналитик)
docs/user-guide.md           — руководство пользователя и примеры запуска (аналитик)
docs/test-report.md          — отчёт о тестировании (QA)
scripts/                     — скрипты решения (разработчик)
tests/test-cases.md          — тест-кейсы (QA)
tests/data/                  — синтетические копии ФС (QA)
.github/ISSUE_TEMPLATE/      — шаблоны задач: баг, «Готов к защите»
```

## 5. Риски

| Риск | Что делаем |
|------|-----------|
| Порча общей ФС, особенно при тестировании удаления в F3 | Разрабатываем и тестируем только на копиях, оригинал не трогаем |
| Требования трактуются по-разному | Задаём вопросы заказчику на этапе запуска |
| Удаление досье испортит данные | Тестируем только на копиях данных; QA отдельно проверяет подтверждение удаления |
| Участник выпал или задерживается | Принцип MVP; менеджер перераспределяет задачи |
| Не успеваем F3 и F4 | База (веха M1) сдаётся в любом случае |

## 6. Вопросы к заказчику (составили менеджер и аналитик)

1. **Посещаемость.** «Наилучшая посещаемость» — это один лидер, топ-N или все с максимальным значением? Считать в абсолютных числах или в процентах?
2. **Период.** Задаётся годами или датами, в каком формате?
3. **Правильные ответы.** Учитываются по всем тестам и предметам? Что выводить, если несколько студентов делят максимум?
4. **Досье.** Что в него входит? Что именно удаляется: файл досье или все упоминания студента в ФС?
5. **Однофамильцы.** Как поступать, если фамилия совпадает у нескольких студентов?
6. **Успеваемость.** Как она считается: средний балл, доля правильных ответов или что-то ещё?
7. **Интерфейс.** Ключи командной строки, интерактивный ввод в терминале или оба варианта?
8. **Язык.** Есть ли ограничения по языку (например, только bash)?
